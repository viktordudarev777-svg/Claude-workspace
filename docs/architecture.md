# Архитектура

## Общая схема

```
        ┌──────────────────────── Телефон ───────────────────────┐
        │  Камера ──┬─→ штрихкод (EAN/UPC)                       │
        │           └─→ снимок ──→ OCR на устройстве (ML Kit)    │
        │                            │ есть текст                │
        └────────────────────────────┼──────────────────────────-┘
                                     ▼
        POST /analyze/{barcode,label,photo}
                                     │
        ┌──────────────────────── Backend ───────────────────────┐
        │  services/AnalysisService — сеть, кеш, история         │
        │      │                                                 │
        │      ├─→ Open Food Facts (по штрихкоду, с кешем)       │
        │      ├─→ Vision / серверный OCR (если включены)        │
        │      │                                                 │
        │      ▼                                                 │
        │  domain/analyzeProduct — чистая функция, без сети      │
        │      разбор состава → поиск добавок → нутриенты →      │
        │      Nutri-Score → находки → оценка → советы           │
        │      │                                                 │
        │      ▼                                                 │
        │  SQLite: история устройства + кеш Open Food Facts      │
        └────────────────────────────────────────────────────────┘
```

## Пакеты

```
packages/engine/   @foodlens/engine   чистый движок анализа
packages/data/     @foodlens/data     JSON-данные + единственный доступ к файлам
backend/           @foodlens/backend  HTTP, интеграции, история
mobile/            foodlens-mobile    камера, OCR, экраны
```

Зависимости идут в одну сторону: `engine` ← `data` ← `backend`, и `engine` +
снимок данных → `mobile`. Движок не зависит ни от чего.

## Почему движок отделён от всего остального

`packages/engine` не импортирует ни Express, ни fetch, ни файловую систему, ни
даже Node API. В его `tsconfig.json` стоит `"types": []`, поэтому это не
договорённость, а то, что проверяет компилятор: попытка позвать `fs` или
`process` не соберётся.

Вход — состав и БЖУ, выход — вердикт. Это даёт четыре вещи:

1. **Тесты без сети.** 96 тестов гоняются на фикстурах и in-memory базе. Ни один
   не зависит от чужого аптайма.
2. **Один и тот же расчёт для «чем заменить».** Кандидаты из Open Food Facts
   пересчитываются тем же кодом, а не сравниваются с чужой оценкой. Иначе
   «лучше» означало бы не то же самое, что видел пользователь.
3. **Офлайн-режим без второй реализации.** На телефоне работает буквально тот же
   пакет, и вердикт совпадает с серверным, а не приближает его.
4. **Данные снаружи.** `analyzeProduct` принимает индекс добавок аргументом.
   Сервер строит его из файлов, приложение — из встроенного снимка или
   скачанного бандла; код индексации один и тот же.

## Офлайн-режим

```
Первый запуск            snapshot.json в бандле приложения (263 КБ, 204 добавки)
                              │
Появилась сеть           GET /api/v1/bundle/version → отличается? → GET /api/v1/bundle
                              │                                          │
                              └──────────── кеш в AsyncStorage ──────────┘
                              │
Разбор без сети          buildAdditiveDatabase(...) → analyzeProduct(...)
                              │
                         очередь в AsyncStorage → при первом успешном запросе
                         тексты этикеток досылаются на сервер
```

Три решения, которые стоит отметить:

- **Снимок закоммичен, а не генерируется при сборке.** Свежий клон собирается без
  подготовительного шага, а расхождение снимка с данными ловит тест.
- **Кеш применяется только если он новее снимка.** Обновление приложения может
  принести справочник свежее последнего скачанного, и тогда побеждает снимок.
- **В очередь попадает исходный текст этикетки, а не готовый результат.** Сервер
  остаётся источником истины: у него может быть более новый справочник, и он
  может найти продукт в Open Food Facts там, где телефон не смог.

Штрихкод офлайн не работает принципиально: данные о продукте живут в Open Food
Facts. Приложение не выдумывает вердикт, а честно сообщает об ошибке и предлагает
сфотографировать состав.

## Поток данных внутри анализа

```
ingredientsText
   │
   ├─→ extractIngredientSection   отрезает «Состав:» и хвост про хранение
   │        │
   │        ├─→ parseIngredients  → список с процентами, вложенностью, рангом
   │        └─→ findAdditives     → три прохода по убыванию уверенности
   │
nutriments (из Open Food Facts или из parseNutritionLabel)
   │
   ├─→ nutrientLights   пороги UK FSA (еда или напиток)
   └─→ computeNutriScore профиль по категории
   │
   ▼
buildFlags → scoreProduct → buildRecommendations
```

### Поиск добавок: три прохода

| Проход | Что ищет | Уверенность |
|---|---|---|
| 1 | E-коды: `E621`, `Е-621` (кириллица), `INS 621`, `E150d` | 0.99 |
| 1' | те же коды, но с починкой цифр после OCR: `E6Z1` → `E621` | 0.75 |
| 2 | синонимы целиком: «глутамат натрия», `monosodium glutamate` | 0.90 |
| 3 | нечёткое совпадение длинных названий (расстояние ≤ 2) | 0.60-0.70 |

Более поздний проход никогда не перекрывает участок текста, занятый ранним, поэтому
продукт, где написаны и код, и название, даёт одну находку, а не две. Уверенность
идёт дальше в оценку: шаткое совпадение по OCR не может утопить продукт так же
сильно, как явно напечатанный код.

### Почему нормализация не сворачивает гомоглифы целиком

Кириллическая «Е» и латинская «E» неразличимы на глаз, и OCR выбирает алфавит по
окружению. Первая версия сворачивала гомоглифы во всём тексте — и превращала «сахар»
в «caxap», создавая ложные совпадения между русскими и английскими словами.
Сейчас свёртка применяется только внутри токена, похожего на E-код
(`canonicalizeECode`), где она и нужна.

Похожая ловушка — `\b` в регулярных выражениях: в JavaScript граница слова определена
по ASCII, поэтому `/жиры\b/` молча не совпадает ни с одной русской этикеткой. Все
шаблоны нутриентов используют явный `(?![\p{L}\p{N}])`.

### Почему таблица БЖУ читается отдельно от состава

Слово «сахар» встречается в составе раньше, чем в таблице пищевой ценности, а число
после него — это часть E-кода, а не граммы. Поэтому `parseNutritionLabel` сначала
сужает текст до блока, начинающегося с «пищевая ценность» / `nutrition` / `nahrwerte`,
и только потом ищет нутриенты. Каждое найденное значение «выжигается» из текста,
чтобы менее специфичный шаблон («жиры») не прочитал уже разобранную строку
(«в том числе насыщенные»).

## Данные

```
packages/data/data/
  references.json          источники: EFSA, IARC, регламент ЕС, FDA, JECFA, ВОЗ
  additives/
    10-colours.json        красители
    11-colours-extra.json
    20-preservatives.json  консерванты и антиоксиданты
    21-preservatives-extra.json
    30-texture.json        загустители, эмульгаторы, стабилизаторы, усилители вкуса
    31-texture-extra.json
    40-sweeteners.json     подсластители
    50-minerals-anticaking.json
    60-misc-extra.json     кислоты, соли, воски, газы
  whole-foods.json         32 цельных продукта и блюда для распознавания по фото
```

Файлы группируются, а не сливаются в один, чтобы правку можно было ревьюить.
Загрузчик читает каталог целиком, проверяет обязательные поля, формат кода,
наличие обоих языков и разрешимость каждой ссылки на источник — и падает при
старте, а не на первом запросе пользователя. Версия данных выводится из их
содержимого, и по ней приложение понимает, что пора обновить справочник.

Добавить добавку — значит дописать запись в JSON. Кода писать не нужно.

## Интеграции

| Провайдер | Роль | Что если недоступен |
|---|---|---|
| Open Food Facts | продукт по штрихкоду, кандидаты для замены | предупреждение, разбор по фотографии |
| Google Vision / Clarifai | распознавание продукта на фото | путь просто выключен |
| Google Vision OCR | серверный OCR для клиентов без своего | клиент отправляет текст сам |

Все три подключаются через переменные окружения и по умолчанию выключены —
приложение работает без единого платного ключа, если пользоваться штрихкодом и
OCR на устройстве.

## Хранение

SQLite, три таблицы: `devices`, `scans` (полный `AnalysisResult` в `payload`, чтобы
история открывалась мгновенно) и `off_cache` (ответы Open Food Facts на неделю —
API ограничивает частоту, а один и тот же товар сканируют повторно).

Схема лежит в TypeScript-константе, а не в `.sql`-файле: так она переживает сборку
без шага копирования, а все выражения идемпотентны и применяются при каждом старте.

## Мобильное приложение

```
App.tsx                стек навигации + табы
src/context/           единственное глобальное состояние: device id и язык
src/api/               типизированный клиент, таймауты, разбор ошибок
src/services/          вызовы анализа с офлайн-фолбэком
src/engine/            сборка справочника на устройстве и офлайн-разбор
src/offline/           очередь сканов, сделанных без сети
src/ocr/               OCR на устройстве с honest-fallback на сервер
src/screens/           Сканер · Результат · История · Справочник · Настройки
src/components/        карточки, светофоры, строки находок
src/theme/             светлая и тёмная темы; три цвета светофора — опорные точки
```

Metro настроен на монорепозиторий (`mobile/metro.config.js`): без `watchFolders`
он не увидел бы движок, который лежит вне каталога приложения. Typecheck такое
не ловит, поэтому CI собирает настоящий бандл и проверяет, что справочник в него
попал — Hermes хранит не-ASCII строки в UTF-16, так что проверка ищет и то, и
другое представление.

Экран результата собран в том порядке, в котором информация нужна покупателю:
вердикт → что не так → что делать → и только потом сырые данные. Оговорки и
уверенность распознавания показываются отдельным блоком, а не прячутся.

Разрешение адреса сервера учитывает, что на телефоне `localhost` — это сам телефон:
если Metro раздаёт бандл по локальной сети, клиент берёт хост оттуда.
